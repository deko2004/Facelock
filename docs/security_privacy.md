# Security and privacy

> For a consolidated Arabic reference on the optional anti-spoofing protection,
> its guarantees and remaining attack surface, see
> [anti_spoofing_summary.md](anti_spoofing_summary.md).

## Scope

This document describes the security properties of the academic demonstration in
this repository. It is a threat-model discussion, not a certification or a
guarantee. The system is **not** suitable for production authentication, access
control, surveillance or identity verification.

## Assets

| Asset | Where it lives | Sensitivity |
|---|---|---|
| Face images | In memory during use; optional annotated exports under `results/` | High |
| SFace embeddings | Encrypted in `database/biometric.db`; decrypted in memory during matching | High |
| Encryption key | `database/templates.key` | Critical |
| Display names, user IDs | SQLite `users` table in plaintext | Personal data |
| Audit events | SQLite `audit_log` table | Operational metadata |
| Threshold setting | `database/app_settings.json` | Low |
| ONNX models | `models/` | Public model files |
| PAD model | `models/anti_spoofing/MiniFASNetV2.onnx` | Public model file (Apache-2.0) |

Biometric data is personal data. Even an embedding derived from a face should be
treated as sensitive because it can support linkage or matching attacks.

## Protections implemented

### Local-only processing

The application does not call a cloud API, send telemetry or make network
requests. Face detection, embedding extraction, matching, storage and evaluation
run on the local machine.

This reduces network exposure but does not protect against local malware,
compromised user accounts or a malicious process running as the same user.

### Optional presentation-attack detection

The Live Camera page can enable MiniFASNetV2 before SFace. When enabled:

- the primary face is cropped with scale `2.7`, resized to `80x80`, kept as BGR
  `float32` in `0..255` (no division by 255) and passed to the ONNX model;
- output index `1` is treated as live and indices `0`/`2` as spoof;
- the face must be live for several consecutive frames before SFace runs;
- a spoof, uncertain, error or no-face result blocks authentication;
- only the primary face is eligible for identity verification;
- a missing model or missing `onnxruntime` produces an explicit error and
  authentication remains blocked while protection is ON.

This is fail-closed for the Live Camera workflow, but it is a demonstration
classifier, not a certified PAD system. It does not provide challenge-response,
depth sensing or a guarantee against masks, replay, deepfakes or novel attacks.
The default thresholds and frame counts are not calibrated on a representative
attack corpus.

### Encryption at rest

Each embedding is serialised as a `float32` array and encrypted with Fernet
(AES-128-CBC with HMAC-SHA256 authentication). A fresh random IV is generated by
Fernet for every token. The database stores the token, not the raw vector.

The key is generated with `Fernet.generate_key()` and stored separately in
`database/templates.key`. The code creates the key with `O_EXCL` and `0600`
permissions, restricts the database directory to `0700` where supported, and sets
the database file to `0600`.

This protects against casual inspection of a copied database or a database file
that is accidentally shared without the key. It does **not** protect against:

- an attacker who can read the whole project directory, including the key;
- malware or a malicious process running as the same OS user;
- a compromised account with access to the key and database;
- memory inspection while a template is decrypted for matching;
- a key that is backed up or copied insecurely.

The key is not stored in a hardware security module, TPM or OS keyring. There is
no key rotation or per-user key derivation.

### Data minimisation

- Enrolment photographs are never written to the database.
- The database stores one encrypted template per user plus basic metadata.
- Audit events contain event type, user ID, score, threshold and source, but not
  images or raw embeddings.
- The GUI shows only a template size, not the vector.
- The evaluation exports contain file paths and similarity scores, not embeddings.

### Input validation

User IDs are restricted to a safe ASCII subset: they must start with a letter or
number and may contain letters, numbers, dot, dash or underscore, up to 64
characters. Display names are limited to 80 characters and control characters
are rejected. SQL queries use parameter binding, not string concatenation.

### Error handling

Expected failures (missing model, no face, duplicate user, wrong key, camera
failure) produce user-facing errors. Audit logging is best-effort and does not
crash a biometric workflow.

## What is not protected

### PAD is optional and not a liveness guarantee

With Anti-Spoofing Protection OFF, the matcher compares embeddings from a still
image or camera frame and does not know whether the face is live, a photograph,
a replay, a mask or a deepfake. A printed photo or screen replay can be accepted
if it produces a sufficiently similar embedding.

With the Live Camera toggle ON, MiniFASNetV2 attempts to detect presentation
attacks before SFace. This raises the bar for simple printed-photo and
screen-replay attacks, but it is not certified and can be bypassed. It does not
cover every attack type, camera, display, printer or lighting condition, and the
default thresholds are not calibrated. The Security & Privacy page's static-image
demonstration bypasses the Live Camera PAD path, so it still illustrates why
recognition alone is not liveness.

A production system would need a certified PAD component, challenge-response,
depth sensing or a combination of controls, plus a realistic PAD evaluation on
representative attack data.

### 1:N name labels can be wrong

The live camera draws the closest enrolled name when the best cosine similarity
passes the threshold. This is open-set 1:N identification, not proof that the
person is that user. The threshold is not calibrated for identification, and
false matches become more likely as the enrolled population grows. The name
label is a demonstration feature; do not use it for access control.

### No demographic bias evaluation

The bundled evaluation sample is tiny and not representative. The system does not
measure false match or false non-match rates across demographic groups, lighting,
pose, age or image quality. No fairness claim is made.

### Threshold is not calibrated

The default `0.363` is OpenCV's published SFace cosine reference for its LFW
calibration. It is a starting point, not a calibrated operating point for this
application. A real deployment would need a validation set, a stated target FAR
or FRR, and a documented calibration procedure.

### Metadata is not encrypted

Display names and user IDs are stored in plaintext in SQLite. Only the biometric
templates are encrypted. A database reader can learn who is enrolled and when.

### Deletion is logical

Deleting a user removes the row and writes an audit event. SQLite may retain old
pages or backups until vacuumed or overwritten. The deleted template remains
encrypted, but the key may still exist. Secure erasure of backups and filesystem
snapshots is outside the application.

### The OS account is part of the boundary

File permissions and process isolation are the main protection for the key. If
another process runs as the same user, it can read the key and database. The
application does not defend against a compromised desktop session.

### Camera trust

The camera path assumes the operating system and device are trustworthy. A
malicious virtual camera or injected frames are outside the threat model.

## Attack scenarios

| Scenario | Effect | Mitigation in this project | Residual risk |
|---|---|---|---|
| Copy `biometric.db` without the key | Templates are unreadable | Fernet encryption | Key may be copied too |
| Read the whole project directory | Templates and key available | File permissions only | Same-user malware wins |
| Present a printed photo | Matcher may accept | Optional MiniFASNetV2 on Live Camera | High when PAD OFF; reduced but not eliminated when ON |
| Replay a video | Matcher may accept | Optional MiniFASNetV2 on Live Camera | High when PAD OFF; reduced but not eliminated when ON |
| Guess a user ID | Reveals enrolment metadata | IDs are not secrets | Enumeration possible |
| Tamper with a template | Decryption/authentication fails | Fernet HMAC | Denial of service |
| Delete a user without authorisation | Enrolment removed | OS account boundary | No app-level roles |
| Inspect process memory | Templates visible during matching | None | High on a compromised host |
| Change the threshold | Alters decisions | Persisted locally; no integrity check | Anyone with file access can edit |

## Privacy recommendations for users

- Obtain explicit consent before enrolling anyone.
- Use a dedicated OS account for the demonstration where practical.
- Do not enrol real people or sensitive identities in a shared environment.
- Delete enrolled users when they are no longer needed.
- Do not commit `database/`, `results/` exports or images of real people to git.
- Treat exported annotated images and CSV files as sensitive.
- Back up the key only if you understand the risk; without it, templates cannot
  be recovered.
- Do not reuse a user ID for a different person.

## Production hardening checklist

If this code were ever to be extended beyond a demonstration, at minimum:

1. Replace the demonstration PAD with certified liveness/PAD and evaluate it
   against a representative presentation-attack corpus.
2. Calibrate the threshold on a representative validation set and document the
   target FAR/FRR.
3. Evaluate demographic and environmental fairness.
4. Move the key to a TPM, OS keyring or hardware security module.
5. Encrypt metadata as well as templates, or minimise it further.
6. Add authenticated roles and audit-log integrity protection.
7. Add secure deletion and backup handling.
8. Threat-model the camera, operating system and update supply chain.
9. Perform independent security review and privacy impact assessment.
10. Comply with applicable biometric privacy law and obtain informed consent.

## Reporting

This is an academic project. Do not deploy it as a security control. If you find
a bug in the demonstration, document it and fix it in the repository rather than
relying on the application to protect real assets.
