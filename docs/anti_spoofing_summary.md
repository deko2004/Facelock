# الحماية من التزييف (Anti-Spoofing / PAD): مرجع شامل

هذا الملف يجمع كل ما يتعلق بحماية الكاميرا المباشرة التي أُضيفت إلى المشروع:
ما تمت إضافته، كيف يعمل، من ماذا يحمي فعليًا، وما الثغرات والهجمات التي لا تزال
خارج نطاق الحماية. المشروع أكاديمي وليس نظامًا إنتاجيًا، وهذا الملف جزء من
التوثيق الأمني وليس ضمانًا أمنيًا.

> **تحديث لاحق:** أُضيف مختبر **Video Injection Lab** لإعادة تشغيل فيديو مسجّل
> عبر نفس مسار PAD، مع سلامة مصدر وحيوية نشطة اختياريتين. التفاصيل الكاملة
> والقيود في [video_injection_lab.md](video_injection_lab.md). يظل هذا الملف
> مرجعًا لطبقة PAD نفسها.

## 1. نطاق الحماية

الحماية المضافة هي **كشف هجمات العرض التقديمي (Presentation Attack Detection)**
باستخدام نموذج `MiniFASNetV2` قبل تشغيل مطابقة الوجه `SFace` في صفحة
**Live Camera**، ويُعاد استخدامه في **Video Injection Lab** عند تفعيل PAD.

الهدف منها تقليل احتمال قبول:

- صورة مطبوعة لوجه شخص.
- إعادة عرض صورة أو فيديو على شاشة هاتف أو جهاز لوحي.
- بعض محاولات العرض البسيطة الأخرى التي يستطيع النموذج تمييزها.

هي **ليست**:

- إثبات هوية.
- ضمان أن الوجه حي في كل الظروف.
- بديلًا عن التحقق متعدد العوامل.
- حماية من هجمات المتسلل الذي يملك الجهاز أو الحساب.
- حماية للمسارات التي تعتمد على الصور الثابتة.

## 3. المسار الكامل للتحقق عند تفعيل PAD

```text
Camera
  -> YuNet face detection
  -> primary/largest face only
  -> MiniFASNetV2 PAD
  -> softmax + thresholds
  -> temporal live streak
  -> LIVE only after required frames
  -> SFace embedding + matching/verification
```

وإذا لم تتحقق الحيوية:

```text
PAD blocked
  -> no SFace identity decision
  -> verified = False
  -> UI shows AUTH BLOCKED / SPOOF DETECTED / HOLD STILL / PAD ERROR
```

### 3.1 التحميل والتفعيل

- PAD اختياري ومغلق افتراضيًا.
- عند تفعيل المفتاح، يُحمّل النموذج في الخلفية.
- إذا كان النموذج أو `onnxruntime` غير متاح، يظهر خطأ صريح ويبقى زر البدء
  معطلًا ما دامت الحماية مفعلة.
- لا يوجد رجوع صامت إلى المطابقة غير المحمية عند فشل PAD.
- يمكن تفعيل PAD أثناء عمل الكاميرا دون إعادة تشغيلها؛ العامل يقرأ حالة
  التشغيل ويتعامل مع تغيرها.

### 3.2 المعالجة المسبقة للنموذج

- المدخل: وجه BGR.
- يُوسّع مربع الوجه بمعامل `2.7` ثم يُقصّ داخل حدود الصورة.
- يُعاد تحجيمه إلى `80x80`.
- يُحوّل إلى `float32` بترتيب `[1, 3, 80, 80]`.
- القيم تبقى في النطاق `0..255`، **بدون قسمة على 255**.
- أي قيمة غير منتهية أو صورة فارغة ترفع خطأ `AntiSpoofingError`.

هذا العقد مطابق لمسار Silent-Face الأصلي، وأي تغيير فيه قد يخفض دقة النموذج
بشكل صامت.

### 3.3 قرار النموذج

- النموذج يعيد 3 logits.
- يُطبق softmax.
- الفهرس `1` هو الوجه الحي/الحقيقي.
- الفهارس `0` و`2` هما هجوم عرض تقديمي.
- `live_score` هو احتمال الفئة `1`.
- `spoof_score` هو أعلى احتمال من الفئتين الأخريين.
- `confidence` هو أعلى احتمال في التوزيع.

القرار الخام:

```text
live_score >= 0.80        -> LIVE
spoof_score >= 0.60       -> SPOOF
otherwise                 -> UNCERTAIN
```

العتبات قابلة للتغيير عبر متغيرات البيئة، لكن القيم الافتراضية غير معايرة على
مجموعة هجمات تمثيلية.

### 3.4 التتبع الزمني

الحيوية لا تُقبل من إطار واحد. `PadTracker` يطبق:

- `PAD_REQUIRED_LIVE_FRAMES = 3` تحديثات حية متتالية قبل السماح لـ SFace.
- `PAD_FRAME_INTERVAL = 2` أي أن استدلال PAD يعمل كل إطارين معادَين، ويعاد
  استخدام آخر تنبؤ في الإطار بينهما.
- `PAD_FACE_IOU_THRESHOLD = 0.35` لتحديد تغير الوجه.
- عند تغير الوجه: إعادة ضبط السلسلة والتنبؤ المخزن.
- عند `SPOOF` أو `UNCERTAIN` أو `NO_FACE` أو `ERROR` أو `LOADING`: لا SFace.
- بعد `SPOOF`، حتى لو عاد الوجه حيًا، يجب بناء سلسلة حيوية جديدة كاملة.
- عند تغير حالة PAD أو تغير النموذج: إعادة ضبط المتتبع والتنبؤ المخزن.
- عند حجب PAD: تُمسح ذاكرة SFace المؤقتة لمنع إعادة استخدام بصمة قديمة.

### 3.5 تقييد الوجه الأساسي

عند تفعيل PAD:

- فقط أكبر/أوضح وجه (primary face) مؤهل للتحقق.
- بقية الوجوه تُعرض عليها علامة `PAD: primary only`.
- لا تُنفذ SFace للوجوه الأخرى ولا تُعطى أسماء هوية.
- هذا يقلل سطح الهجوم لكنه يعني أن الوجوه المتعددة ليست محمية/متحققة جميعًا.

## 4. حالات PAD ومعنى كل حالة

| الحالة | المعنى | هل يسمح بـ SFace؟ |
|---|---|---|
| `DISABLED` | الحماية مغلقة | نعم، المسار الأصلي بدون PAD |
| `READY` | النموذج محمّل وجاهز (حالة واجهة) | لا ينطبق قبل بدء الكاميرا |
| `LOADING` | جارٍ تحميل النموذج | لا |
| `ERROR` | فشل التحميل أو الاستدلال | لا |
| `NO_FACE` | لا يوجد وجه | لا |
| `ANALYZING` | يجمع أدلة الحيوية | لا |
| `LIVE` | تحققت الحيوية بعد السلسلة المطلوبة | نعم |
| `SPOOF` | هجوم عرض تقديمي | لا |
| `UNCERTAIN` | الثقة منخفضة | لا |

## 5. الإعدادات الافتراضية

| المتغير | الافتراضي | الأثر |
|---|---:|---|
| `FACE_PAD_MODEL` | `models/anti_spoofing/MiniFASNetV2.onnx` | مسار النموذج |
| `FACE_PAD_LIVE_THRESHOLD` | `0.80` | حد قبول الحيوية |
| `FACE_PAD_SPOOF_THRESHOLD` | `0.60` | حد اعتبار النتيجة هجومًا |
| `FACE_PAD_REQUIRED_LIVE_FRAMES` | `3` | عدد التحديثات الحية المتتالية |
| `FACE_PAD_FRAME_INTERVAL` | `2` | تكرار استدلال PAD |
| `FACE_PAD_FACE_IOU_THRESHOLD` | `0.35` | حساسية تغير الوجه |
| `FACE_PAD_THREADS` | `1` | خيوط ONNX Runtime |
| `FACE_DIAGNOSTICS` | `0` | إظهار زمن PAD وبقية التشخيصات |

ثوابت غير قابلة للتغيير عبر البيئة حاليًا:

- `PAD_CROP_SCALE = 2.7`
- `PAD_INPUT_SIZE = 80x80`
- `PAD_CLASS_LIVE_INDEX = 1`

## 6. من ماذا تحمي فعليًا

بشكل واقعي، الحماية تقلل خطر:

- صورة مطبوعة بسيطة تُعرض أمام الكاميرا.
- إعادة عرض صورة أو فيديو على شاشة في ظروف إضاءة/زاوية مناسبة للنموذج.
- استمرار التحقق بعد اختفاء الوجه أو تغيره.
- قبول وجه غير حي عند فشل النموذج أو غيابه أو حدوث خطأ.
- استخدام بصمة SFace قديمة بعد حجب PAD.

لكن كلمة “تحمي” هنا نسبية: النموذج قد يخطئ في الاتجاهين، والاختبارات الحالية
تثبت التكامل والفعالية الأولية على عينات صغيرة، وليس الأمان ضد مهاجم محترف.

## 7. الثغرات والهجمات التي لا تزال بلا حماية

هذا هو الجزء الأهم: PAD الحالي طبقة دفاع إضافية، وليس حماية كاملة.

### 7.1 حدود نموذج PAD نفسه

- **ليس PAD معتمدًا**: لا يوجد اعتماد أمني أو تقييم مستقل.
- **لا يوجد ضمان ضد الهجمات المتطورة**: الأقنعة عالية الجودة، الأقنعة ثلاثية
  الأبعاد، إعادة العرض المتقدمة، الفيديو المزيف، والتزييف العميق قد تتجاوز
  النموذج.
- **الهجمات التخريبية (Adversarial)**: تعديلات دقيقة في الصورة قد تخدع النموذج.
- **عدم معايرة العتبات**: `0.80` و`0.60` ليستا معايرتين على كاميرات وطابعات
  وشاشات وظروف إضاءة ومجموعات هجوم تمثيلية.
- **غياب تقييم التحيز**: لا يوجد تقييم عبر لون البشرة، العمر، الجنس، الإضاءة،
  الزوايا، النظارات، أو نوع الكاميرا.
- **لا توجد مقاييس PAD قياسية**: لا يوجد قياس `APCER` و`BPCER` و`ACER` على
  مجموعة هجمات حقيقية.
- **النموذج من طرف ثالث**: المشروع لا يضمن جودة تدريبه أو خلوه من نقاط ضعف
  غير معروفة.

### 7.2 نافذة زمنية بين استدلالات PAD

- PAD يعمل كل إطارين افتراضيًا، ويعاد استخدام آخر تنبؤ في الإطار الفاصل.
- إذا استُبدل وجه حي بآخر في نفس الموضع تقريبًا، فقد يظل `IoU` أعلى من `0.35`
  ولا يُكتشف “تغير الوجه”.
- يمكن أن تبقى أدلة الحيوية/بصمة SFace المؤقتة صالحة لإطار أو أكثر بعد اختفاء
  الوجه الحي.
- هذا لا يمنح المهاجم هوية شخص آخر مباشرة، لكنه قد يُبقي قرار “VERIFIED” أو
  “LIVE” نشطًا لفترة قصيرة بعد زوال الوجه الحي.
- مربع الوجه المستخدم في PAD قد يكون من كشف قديم بإطار واحد، ما قد يسبب رفضًا
  خاطئًا عند الحركة السريعة أو تغير الإضاءة.
- التخفيف المتاح: `FACE_PAD_FRAME_INTERVAL=1` وتقليل فترات إعادة استخدام
  الميزات، لكنه يزيد استهلاك المعالج.

### 7.3 غياب التحدي والتفاعل

- لا يوجد `challenge-response` في صفحة **Live Camera** نفسها مثل طلب الالتفات،
  الوميض، تحريك الرأس، أو نطق كلمة.
- مختبر **Video Injection Lab** يضيف تحدي حركة رأس عشوائيًا (يسار/يمين/أعلى/
  أسفل) من معالم YuNet، لكنه عرض أكاديمي وليس كشف حيوية معتمدًا.
- لا يوجد تحليل حركة/عمق/parallax.
- لا توجد كاميرا IR أو حرارية أو متعددة الأطياف.
- لا يوجد كشف عمق أو بنية ثلاثية الأبعاد.
- لذلك قد ينجح فيديو مسجل أو إعادة عرض متقنة إذا صنّفها النموذج كحيوية، أو إذا
  كان الفيديو نفسه ينفذ الحركة المطلوبة.

### 7.4 PAD لا يغطي كل مسارات التطبيق

الحماية مضافة إلى صفحة **Live Camera** وإلى **Video Injection Lab** عند تفعيل
PAD. المسارات التالية لا تطبق PAD افتراضيًا:

- **Enrolment من صورة**: يمكن تسجيل وجه من صورة ثابتة.
- **Enrolment من الكاميرا**: نافذة التقاط الصورة لا تمرر `pad_runtime`.
- **Verification من صورة**: لا يوجد PAD.
- **Verification من الكاميرا**: يستخدم عامل الكاميرا لكن بدون PAD.
- **Compare Images**: مقارنة صورتين ثابتتين بدون PAD.
- **Security page**: عرض الصورة الثابتة للتزييف يتجاوز PAD عمدًا لتوضيح الفكرة.
- **Video Injection Lab**: يطبق PAD حسب الوضع المختار، لكنه مسار عرض أكاديمي
  وليس مسار تحقق إنتاجيًا.

أي استخدام لهذه المسارات كتحقق أمني يظل معرضًا لهجمات الصور وإعادة العرض.

### 7.5 يمكن تعطيل الحماية

- أي شخص لديه وصول إلى واجهة المستخدم يمكنه إلغاء تحديد
  **Anti-Spoofing Protection**.
- لا توجد سياسة إلزامية أو صلاحيات أو كلمة مرور إدارية تمنع التعطيل.
- لا توجد حماية من تغيير متغيرات البيئة أو ملفات الإعداد.
- لا يوجد تحقق من سلامة النموذج عند التحميل؛ ملف `SHA-256` موثق لكنه غير
  مُتحقق منه تلقائيًا.
- من يملك وصولًا إلى ملفات المشروع يمكنه استبدال النموذج أو تعديل الكود.

### 7.6 الثقة بالكاميرا ونظام التشغيل

- كاميرا افتراضية خبيثة أو إطارات محقونة قد تتجاوز PAD.
- فحص سلامة المصدر في المختبر اجتهادي على مستوى التطبيق وليس توثيقًا تشفيريًا
  للكاميرا؛ يمكن تجاوزه عبر نظام التشغيل أو التعريف أو الكاميرا الافتراضية.
- برنامج تشغيل كاميرا مخترق أو نظام تشغيل مخترق خارج نطاق الحماية.
- لا توجد حماية من إعادة تشغيل الكاميرا أو قطع الاتصال أو تجميد الصورة.
- لا توجد حماية من هجمات إعادة التشغيل على مستوى الجهاز أو النظام.
- لا توجد حماية من التلاعب بالعتاد أو firmware.

### 7.7 حدود المطابقة البيومترية

- PAD يثبت (تقريبًا) أن الوجه حي، لكنه لا يثبت أنه الشخص المطلوب.
- التعرف 1:N يعرض أقرب اسم فوق الوجه، وقد يكون خاطئًا.
- عتبة `0.363` غير معايرة لهذا التطبيق.
- كلما زاد عدد المسجلين، زاد احتمال المطابقة الخاطئة.
- لا توجد معايرة لكل مستخدم أو لكل بيئة.
- لا توجد حماية من استخدام وجه شخص حي ومخوّل (coercion أو impersonation).

### 7.8 حدود التخزين والخصوصية

- مفتاح التشفير وقاعدة البيانات في نفس مجلد المشروع.
- برنامج خبيث يعمل بنفس حساب المستخدم يستطيع قراءة المفتاح والقاعدة.
- القوالب تُفك تشفيرها في الذاكرة أثناء المطابقة.
- لا يوجد `TPM` أو `HSM` أو `OS keyring`.
- لا توجد إدارة مفاتيح أو تدوير مفاتيح.
- أسماء المستخدمين وبيانات التعريف مخزنة كنص صريح.
- سجل التدقيق غير محمي ضد التعديل.
- الحذف منطقي وليس محوًا آمنًا؛ قد تبقى صفحات SQLite أو نسخ احتياطية.
- لا توجد حماية لنسخ قاعدة البيانات الاحتياطية.

### 7.9 غياب الضوابط التشغيلية

- لا يوجد تسجيل تدقيق خاص بقرارات PAD أو محاولات التزييف.
- لا تُحفظ حالة PAD أو أدلة الحيوية بعد إغلاق الصفحة أو التطبيق.
- لا توجد تنبيهات أو مراقبة أمنية.
- لا يوجد rate limiting أو lockout بعد محاولات فاشلة متكررة.
- لا توجد أدوار أو صلاحيات أو مصادقة متعددة العوامل.
- لا توجد سياسة خصوصية أو تقييم أثر حماية بيانات مطبقة.
- لا توجد حماية من الإكراه أو الاستخدام القسري لوجه شخص مخوّل.

### 7.10 جدول موجز للهجمات المتبقية

| الهجوم | الحماية الحالية | الخطر المتبقي |
|---|---|---|
| صورة مطبوعة بسيطة | PAD اختياري + عتبات + سلسلة زمنية | يقل الخطر، ولا يزول |
| إعادة عرض على شاشة | PAD اختياري | يقل الخطر، وقد ينجح بعرض متقن |
| قناع ثلاثي الأبعاد | لا يوجد كشف عمق/IR | مرتفع |
| فيديو مسجل/Deepfake | لا يوجد challenge-response | مرتفع |
| استبدال الوجه بنفس المربع | تغير الوجه عبر IoU فقط | نافذة زمنية قصيرة |
| تعطيل PAD من الواجهة | لا توجد سياسة إلزامية | مرتفع مع وصول محلي |
| كاميرا افتراضية/إطارات محقونة | لا توجد حماية | مرتفع |
| استبدال النموذج أو تعديل الكود | SHA موثق غير مُتحقق | مرتفع مع وصول للملفات |
| سرقة القاعدة والمفتاح | تشفير + صلاحيات ملفات | مرتفع مع نفس المستخدم |
| قراءة الذاكرة | لا توجد حماية | مرتفع على جهاز مخترق |
| مطابقة خاطئة 1:N | عتبة غير معايرة | يرتفع مع حجم القاعدة |
| إكراه شخص مخوّل | لا توجد حماية | خارج نطاق النظام |

## 8. الاختبارات والتحقق

### 8.1 اختبارات آلية

```bash
venv/bin/python -m pytest
```

تغطي الاختبارات:

- عقد مدخلات/مخرجات ONNX.
- المعالجة المسبقة `0..255` بدون `/255`.
- عينات Silent-Face الحقيقية (genuine/attack).
- إعادة عرض شاشة اصطناعية.
- الحاجة إلى تحديثات حية متتالية.
- إعادة الضبط عند تغير الوجه.
- منع SFace عند `SPOOF` و`ERROR` و`NO_FACE`.
- تشغيل SFace بعد سلسلة حية.
- تعذر تحميل النموذج أو فشل الاستدلال.

هذه الاختبارات تثبت التكامل والسلوك المتوقع، وليست تقييمًا أمنيًا شاملاً.

### 8.2 تحقق يدوي

1. شغّل `./run.sh --check` وتأكد من تحميل PAD.
2. افتح **Live Camera** وفعّل **Anti-Spoofing Protection**.
3. اعرض وجهًا حيًا وتأكد من ظهور `LIVE FACE` ثم `VERIFIED` عند وجود هدف.
4. اعرض صورة مطبوعة أو صورة على شاشة هاتف.
5. تأكد من ظهور `AUTH BLOCKED` أو `SPOOF DETECTED` وليس `VERIFIED`.
6. غطِّ الوجه أو أبعد الكاميرا وتأكد من `NO FACE` / `HOLD STILL`.
7. أوقف PAD وتأكد من عودة السلوك الأصلي دون إعادة تشغيل الكاميرا.
8. أعد تشغيل التطبيق مع `FACE_DIAGNOSTICS=1` لمراقبة زمن PAD.

### 8.3 قياس الأداء

```bash
venv/bin/python scripts/benchmark_performance.py --camera --pad --seconds 5
```

PAD يضيف زمن استدلال، لكنه يعمل على الوجه الأساسي فقط وكل إطارين افتراضيًا،
وبخيط ONNX واحد. القياسات تختلف حسب المعالج والكاميرا والحمل.

## 9. توصيات لرفع مستوى الحماية

مرتبة حسب الأولوية:

1. **لا تستخدم المشروع كضابط وصول حقيقي**؛ فهو عرض أكاديمي.
2. **لا تعتمد على مسارات الصور الثابتة** للتحقق الأمني.
3. **عاير العتبات** على بيانات تمثيلية للهجمات والظروف البيئية.
4. **قِس APCER/BPCER/ACER** على مجموعة هجمات حقيقية، وليس عينات قليلة.
5. **اعتمد challenge-response** أو عمقًا/IR/تحليل حركة خارج إطار العرض
   الأكاديمي، مع معايرة واختبار مقاومة إعادة العرض.
6. **قلل `FACE_PAD_FRAME_INTERVAL` إلى 1** في السيناريوهات الحساسة.
7. **امنع تعطيل PAD** عبر سياسة إلزامية أو صلاحيات.
8. **سجّل قرارات PAD ومحاولات التزييف** في سجل تدقيق محمي.
9. **أضف rate limiting وlockout** ومصادقة متعددة العوامل.
10. **تحقق من SHA-256 للنموذج عند التحميل** ووقّع النماذج والإعدادات.
11. **انقل المفتاح إلى OS keyring/TPM/HSM** وفعّل تدوير المفاتيح.
12. **شفّر بيانات التعريف** ووفر محوًا آمنًا ونسخًا احتياطية محمية.
13. **عامل الكاميرا ونظام التشغيل كمكونات غير موثوقة** ووثّق حدود الثقة.
14. **أجرِ مراجعة أمنية مستقلة وتقييم أثر خصوصية** قبل أي استخدام واقعي.

## 10. خلاصة سريعة

الحماية المضافة هي طبقة PAD اختيارية وفشل مغلق في صفحة الكاميرا المباشرة،
تمنع تشغيل SFace قبل أدلة حيوية متتالية، وتتعامل مع تغير الوجه وفشل النموذج
بشكل آمن نسبيًا. ويضيف مختبر Video Injection Lab سلامة مصدر وتحدي حركة رأس
اختياريين، مع إعادة استخدام PAD. لكنها:

- لا تحمي المسارات الثابتة.
- لا تحمي من الهجمات المتطورة أو الأقنعة أو الفيديو المزيف.
- تحدي الحركة في المختبر يمكن أن ينجح مع فيديو مسجّل ينفذ الحركة المطلوبة،
  وسلامة المصدر لا تصمد أمام من يتحكم بنظام التشغيل أو التعريف.
- لا تحمي من تعطيل المفتاح أو استبدال النموذج أو اختراق الجهاز.
- لا تحمي من سرقة المفتاح أو قراءة الذاكرة.
- لا تصلح وحدها كضابط وصول إنتاجي.

لذلك يجب التعامل معها كـ **دفاع في العمق** وليس كحماية كاملة.
